# PDF-спецификация → XLSX

**Один движок (spec_engine.py), 5 шагов. Только probe/tables/build. Без flatten/spread.**

## Процесс (5 шагов, строго)

### Шаг 1. PROBE
```bash
python scripts/spec_engine.py probe <pdf>
```
`=== SPEC_PAGES:` — страницы спецификации. Если none — завершить.

### Шаг 2. TABLES
```bash
python scripts/spec_engine.py tables <pdf> --pages N,M,... 2>/dev/null
```
Сохрани JSON. Удали pymupdf-варнинг из начала (строка «Consider using...»), если он сломал JSON.

### Когда текстового слоя НЕТ (vision emergency)

Если tables пуст или probe вернул SPEC_PAGES=none, но PDF содержит векторные кривые/изображения таблиц:

1. **Рендер @200 DPI** (pymupdf page.get_pixmap(dpi=200)) → PNG per page.
2. **vision_analyze каждой страницы** последовательно (не параллельно — локальная модель таймаутит на concurrent-нагрузке). Каждую страницу записывать на диск как data/p{N}.json — per-page JSON = чекпоинт.
3. **Агрегация** per-page JSON → flat list (скрипт-агрегатор).
4. **LLM → rows.json** с имплементацией паттернов A–F ПРЯМО из flat (при vision tables недоступны). **Никакого builder-скрипта, который решает структурные решения — только LLM.**
5. **Build** через spec_engine.py как обычно.

**Анти-цикл (FOCUS) при vision-верификации:**
- **Перед любой верификацией — оценить стоимость.** Один кроп = fitz-рендер (30–120 с) + vision API (20–60 с) = ~2–4 мин реального времени + риск таймаута сессии (>420 с). Если цена > ROI символа → best-effort + флаг, без кропа.
- **Порог: если неоднозначность касается ≤3 символов в неключевом поле (не qty, не DN/∅) → флаг, не кроп.**
- **Макс 1 кроп на одно поле за всю сессию.** При промахе/таймауте → низкоресурсный full-page re-read (целая страница через vision_analyze). Если и это не сработало → принять чтение full page + флаг в финальный отчёт.
- **После любого кропа (успех/неудача) → немедленно rows.json + build. Без второго раунда верификации.** Следующая неоднозначность решается best-effort.
- «Ты застрял в цикле!» — сигнал остановить кропы + принять best guess + флаг. НЕ перечитывать данные с диска.

**Нормализация круглых размеров при vision:**
vision читает диаметры как «Ф125», «ф160», «Φ900» (в разном регистре). Нормализовать ТОЛЬКО когда ф/Ф/Φ + цифры → ∅ + цифры. **Не blanket-транслитерация** — «ФОК», «Фл» не трогать.
regex: `r'(^|\s)([фФΦ])\s?(\d+(?:[.,]?\d+)?)'` → `\1∅\3`
**SIZE_RE по умолчанию (включает все варианты диаметра):**
```python
SIZE_RE = re.compile(r'^[фФΦ∅Ø]\s?\d+(?:\.\d+)?$|^\d{2,5}\s?[хxХ]\s?\d{2,5}$')
```

**Мать-ребёнок (ОВ, формат сданных 2.1–2.3):**
- Классификация в СТРОГОМ порядке: Z → D (header) → C (marker) → B (bare size) → Pattern A → mother (всё остальное без qty) → leaf.
- мать = строка без qty, остаток после исключения header/marker/bare-size. type может быть (ГОСТ у воздуховодов).
- ребёнок (голый размер) наследует полное имя матери: `name = f"{last_mother} {size}"`.
- мать остаётся отдельной строкой (name только, qty пусто).
- дети размеров наследуют type от матери, если у них нет своего type.
- **ВАЛИДАЦИЯ после первого прохода (post-pass):**
  a) Найти все строки где name — голый размер (матчит SIZE_RE) и qty не пусто — это сироты (не нашли мать).
  b) Для каждого сироты: back-search до последней строки без qty, которая НЕ header/marker/bare. Если нашли → это мать сироты. name = mother_name + ' ' + size.
  c) Если mother не нашлась за 10 строк или конец раздела (header/marker) → флаг в отчёт, name оставить как есть.  
  d) Проверить: сумма child_inherited + исправленные сироты == общее количество bare-size строк.

### Шаг 3. LLM → rows.json (ИЗ tables, НЕ flat)

Прочитай tables JSON напрямую. В нём сохранён порядок строк каждой таблицы — это критично. Применяй только ПОСЛЕДОВАТЕЛЬНЫЕ паттерны (relationship между соседними строками, не содержимое):

**Паттерн A — Многострочная позиция:**
Две строки подряд: [name+supplier, без qty] → [продолжение name + type + qty].
Признак: вторая строка начинается со строчной буквы, спецсимвола, «с », «и », «220», «3/».
**ВАЖНО: только строчная буква. Прописная С («Системы», «Секция») НЕ совпадает — иначе заголовки разделов сольются с предыдущей строкой.**
Действие: склеить name, взять type/supplier/qty из второй строки.

**Паттерн B — Размер-ребёнок:**
[строка с полным именем материала/изделия + type, без qty] → [одна ИЛИ НЕСКОЛЬКО строк с размером + qty].
Размер = ∅, ×, Δ=, число-на-число (500х300).
Действие: каждая строка-размер = item с name = имя матери + размер.
Стоп: когда встречается строка, не являющаяся размером.

**Паттерн C — Систем-маркер:**
Короткая строка вида 1-П1, 2-В1, 3-КДУ1… (одна в ячейке name или poz):
- Если следующая строка — полное описание (установка в составе:) → header, не сливать.
- Если дальше идут размеры → мать (паттерн B).

**Паттерн D — Заголовки разделов:**
Строка name в ВЕРХНЕМ регистре ИЛИ заканчивается на «:» И содержит слово (СИСТЕМА, АРМАТУРА, Трубопроводы, Оборудование…) → header.

**Паттерн E — Строка dash (ВК):**
Строка где poz='—' → ребёнок предыдущей матери. name = имя матери + имя ребёнка. poz убрать.

**Паттерн F — Строка с дефисом в name:**
name начинается с «- » → убрать дефис. Это ребёнок состава (в составе:). name самостоятельный, не наследует.

**Паттерн Z — Мусор:**
«Взам. инв.N», «Подпись и дата», «Инв.N подл.», «Изм. Ко», страница-цифра, пустая → удалить.

**Алгоритм (идти сверху вниз, по порядку строк таблицы):**
1. Z → удалить
2. D → header
3. C с полным описанием ниже → header
4. C без имени ниже или с размерами → мать, применить B к následующим
5. A → склейка
6. B после матери → наследование
7. E → ребёнок
8. F → ребёнок сборки
9. Всё остальное → item

Не проверяй содержимое имени (нет списка «Клапан», «Воздуховоды», «Дроссель»). Только паттерны.

Запиши rows.json и ОБЯЗАТЕЛЬНО сохрани рядом с ним tables JSON и номер строчки из него для каждой записи (поле _ti).

### Шаг 4. BUILD
```bash
python scripts/spec_engine.py build rows.json out.xlsx
```
Стили: hdr 4472C4, секции D9E2F3 в B. CSV рядом (; utf-8-sig).

### Шаг 5. Анализ перед выдачей
Проверить против tables JSON:
1. Все страницы и строки таблиц представлены (или объяснимо удалены как мусор).
2. Нет пустых имён.
3. Нет item c qty и именем-только-размер (должен наследовать мать по паттерну B).
4. Нет контаминации: два раздела в одном name.
5. Количество записей ≈ количество не-мусорных строк в tables.

Только после проверок — Lark-уведомление.

### Шаг 5a. Post-pass валидация mother-child
После построения rows.json и до build:
1. Найти все строки с qty и именем-только-размер (SIZE_RE). **Это сироты — мать не распознана.**
2. Для каждого сироты: backwards search через rows (не через flat — в rows уже есть склейки) до последней строки без qty, которая не header/marker/bare. Если нашли → name = mother_name + ' ' + size.
3. Проверить: нет записей с «ф»/«Ф»/«Φ» в позиции диаметра (должно быть «∅»).
4. Проверить: нет отдельных строк «с электродвигателем...» (не слитые продолжения).
5. Проверить: сумма child_inherited + исправленных сирот == количеству записей с SIZE_RE-именем.

## Правило
- flat.json НЕ ИСПОЛЬЗУЕТСЯ. LLM читает tables JSON — там сохранена последовательность строк.
- Никаких builder-скриптов. Шаг 3 — единственный способ построить rows.
- Починка/правка spec_engine.py — только с подтверждения.
- RFQ_Pipeline не трогать.

## Base rules (standards, не шаг)

- **Транскрибировать дословно, что напечатано.**
  Не искать логику/арифметику в данных спецификации — в них могут быть ошибки. Флаги нестыковок — только в финальный отчёт для человека.
- **Системные batch-фиксы, не точечные патчи.**
  Если один misread повторяется на N страницах — batch-fix по всем data/*.json, не правка по одному. Каждый патч должен быть проверяемым (статистика до/после).
- **Список известных misread vision** — `references/vision-misreads.md`. Перед каждым прогоном проверять, какие паттерны применимы к текущему файлу (стиральная доска, не исчерпывающий).
