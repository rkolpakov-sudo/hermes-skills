# Changelog: VK-шаблон интеграция в spec-pdf-csv

## Что случилось

При конвертации `3924-2-МСП-ВК2.1.pdf` (внутреннее водоотведение) существующий
пайплайн `extract_spec.py` отдал **0 записей** — хотя PDF содержит спецификацию
из 47 строк на 3 листах (страницы 12-14). Причина: `find_tables()` не детектит
таблицу ВК-шаблона — её границы не совпадают с шаблоном линий, ожидаемым
PyMuPDF.

## Корень проблемы

`extract_spec.py` завязан на один источник истины — `page.find_tables()`.
Это работает для ОВ (вентиляция/отопление), где спецификация на поздних
страницах в формате «шапка из 9 колонок». ВК-шаблон:

- спецификация на **страницах 12-14** (а не 26+)
- **нет** маппинга по тексту шапки — `find_tables()` находит 20 таблиц
  (штампы, экспликации), но не саму спецификацию
- текстовая геометрия: A3 landscape, 9 колонок с фиксированными x-диапазонами
- на каждой странице колоночный ряд (цифры 1..9), который НЕ является данными
- номер позиции вертикально центрирован в блоке строки (не всегда первой строкой)
- имена с переносом: вторая строка без номера позиции — принадлежит предыдущей

## Механика новой ветки

### 1. Template detection (`scripts/detect_template.py`)

```python
# Вывод: OV | VK | unknown
python detect_template.py <pdf>
```

Логика:
- find_tables() на первых страницах → если есть «Поз.» + 3+ ключевых колонки → OV
- текст «СИСТЕМА К» на странице 12 → VK
- заголовок «внутреннего водоотведения»/«ВК» на стр.1 → VK

Gate в SKILL.md: если `VK` → заменять `extract_spec.py` на `extract_spec_vk.py`
во всех последующих шагах (разведка, доставка, сборка XLSX).

### 2. Координатный парсер (`scripts/extract_spec_vk.py`)

Импортирует `classify`/`qa`/`clean_name`/`clean_text` из `extract_spec.py`
(динамический exec). Единый интерфейс CLI: те же `--debug`, `--out-dir`, `--sep`.

**Алгоритм:**
1. Постранично (только 12-14, 0-indexed 11-13):
   - y-окна таблицы: p12(122-638), p13(44-728), p14(44-420)
   - загрузка слов через `page.get_text("words")`
   - кластеризация в визуальные линии (tolerance 4pt)
   - удаление колоночного ряда (≥5 одноцифровых слов на одной линии)
2. Анкоры: числа в колонке позиции (x 60-105)
3. Интервал строки: от середины с предыдущим анкором до середины со следующим
4. Раскладка по колонкам через жёсткие x-диапазоны:
   - poz:   60-105
   - name:  108-495
   - type:  495-745
   - code:  заглушка (пусто)
   - supplier: 745-885
   - unit:  885-935
   - qty:   935-1000
   - mass:  1000-1060
   - note:  1060+
5. Секционные заголовки (СИСТЕМА К1/К2/К13) — наследуются через страницы

**Ключевые грабли (пойманы и устранены):**
- Первая строка: интервал от y_top, не от -inf (иначе захватывает заголовки)
- Последняя строка: интервал до y_bot, а не до 750 (иначе захватывает титульный блок)
- Мультилайн имена: вторая строка (y+~14pt) — принадлежит строке, а не висит orphan
- Колоночный ряд (1..9) — не анкор (проверка: ≥5 одноцифровых)
- Секция К1 на странице 13 наследуется с листа 1 (global_sec, а не per-page)

- single_letter_tokens ['к','с','и'] — артефакт рендеринга (слово «как»
  на x≈483 вылезает в колонку имени, «аналогТУ» — слитное слово)

## Хорошо бы вынести в будущем

- **detect_vk_pages** — сейчас зашиты константы (PAGE_RANGES, COLS). Если
  следующий ВК-документ будет на других страницах — придётся менять код.
  Лучше: страницы определять по «листов N» из нижнего штампа PDF.
- **x-диапазоны** — считывать из заголовков таблицы или висячих линий,
  а не зашивать.
- **Многолистовые секции** — сейчас K2 начинается на стр.13, заканчивается
  на стр.14. Это завязано на хардкод y_bot. Лучше: детектить «Лист 2/3»,
  «Лист 3/3» из штампа.
